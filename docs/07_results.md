# 07 · Results

All tables are in `results/RESULTS.md`, generated by `scripts/run_experiments.py`
(deterministic, about 30 s). This document summarizes them and says what each number
does and does not show.

Standing caveats:

* **Scripted stand-ins.** Every number comes from scripted model stand-ins under an ideal
  planner (`02_threat_model.md`). The numbers characterize *defense structure*, not any
  real LLM.
* **Resampling unit.** The unit is the base task (9 units), so CIs are wide.
* **Scope.** "CUA" is committed unauthorized actions over families A + B + C (459 cases).
  "Safe failure" is measured on the 246 clean + C cases that have at least one expected
  action (`C_condition` expects none).

## 2. The core question, answered within the assumptions

*Can an agent be unaffected by malicious instructions and still react correctly to
legitimate fact changes?* Within V1–V3 and P1, and in this simulation, **yes, with a
residue that the reference's capability determines**. EP at k = 4:

| family | EP outcome | what produces it |
|---|---|---|
| **A** (instruction, facts fixed) | 100% utility, 0% CUA | R1: documents never add calls. Directive redirects are never extracted as claims. A reader-payload value is extracted (ρ = 1) but never bound, because the user's record (or a lookup) is confirmed first. |
| **B** (false or contradictory facts) | 100% utility, 0% CUA (98% utility at k = 2) | The user's record is confirmed first; false challengers are never bound. `B_same_name_mule` is handled only because the record is confirmed first. |
| **C** (legitimate change) | 84% utility, 0% CUA; the other 16% are safe failures | A changed value is bound once the reference confirms it. The failures are `C_silent`, `C_suppressed` and `C_silent_attacked` on the 4 confirm-only tasks (12/27 each). There the true new value never reaches the resolver as a candidate (no document states it, or a ρ = 1 payload suppresses it), and a confirm-only reference cannot supply it. |
| **D** (delegated counterparty) | 0/3 legitimate bills paid; 0/3 tampered bills paid | There is no grant-fixed entity to verify against, so EP refuses both. This is the price of R1. |

This answer does **not** rest on a new mechanism (§4).

## 3. Where EP differs from the strongest existing defenses

**Only in the confirm-only cells.** Against CaMeL (strong plan) the difference lies in
one cell (authority × confirm-only). Against Fides it lies in both confirm-only cells.
Where a lookup reference exists, there is no difference. Per cell, EP minus X, Δ utility /
Δ CUA (pp), at k = 4 (results §3):

| vs | authority × confirm-only (3 tasks) | data × confirm-only (1 task) | data × lookup (5 tasks) |
|---|---|---|---|
| CaMeL (strong plan) | +26 / 0 | 0 / 0 | 0 / 0 |
| Fides (strong plan) | +32 / −7 | +6 / −12 | 0 / 0 |
| Fides (arg-level P-T) | +46 / 0 | +29 / 0 | 0 / 0 |
| Reference-only | +49 / 0 | +29 / 0 | 0 / 0 |

**Against CaMeL (strong plan)** the whole difference is 45 cases at k = 4 (12 at k = 2).
They are C cases on the three authority × confirm-only tasks, where the new account or
part number appears only in a document. CaMeL's policy cannot accept a document value in
an authority argument, even a reference-confirmed one, so it escalates. EP binds it.
Where a lookup reference exists, both designs fetch the value by the trusted id and
agree exactly.

**Against Fides (strong plan)** there are two differences:

* *EP is safer.* When a verifier refutes the store, Fides passes the newest `query_llm`
  value unverified, which P-T on the context allows. This commits the false value in
  `C_race` and `C_silent_attacked` on three of the four confirm-only tasks (18 commits,
  3.9% CUA).
* *EP is more useful* on the same tasks, but it spends more verification (+0.31
  calls/case).

## 4. The transplant test: the gain is one rule

Five transplants add EP's endorsement rule and resolver to another framework:

* CaMeL, with the rule on authority arguments only;
* CaMeL, with the rule on all fact arguments;
* Fides' typed escape hatch;
* AgentSentry with a verify prompt;
* the firewall with a verify prompt.

**Every transplant produces the same outcome as EP in every one of the 486 cases, at
k = 2 and at k = 4** (results §4, "cases with different outcome" = 0). They differ only
in cost: AgentSentry + verify prompt makes 22.0 LLM calls per case against EP's 2.65.

Two caveats limit what this shows:

* **Three of the five transplants reach parity by construction.** The Fides, AgentSentry
  and firewall transplants resolve facts with EP's resolver, the latter two at perfect
  adherence to a "verify prompt" that is not actually modeled as a prompt (audit FID-4,
  AS-2). Only the CaMeL transplants are a partial test. The policy predicate changes,
  and the policy-aware plan therefore also verifies document values for authority facts
  (it now uses the shared resolver policy). Halting and readers logic stay as they are.
  What the transplants test is that each framework's own policy layer *admits* the
  endorsed value. Whether a real prompted agent would follow the rule is untested.
* **Under verification omission (ω > 0) the scope of the rule matters** (results §9).
  Requiring evidence for *every* FACT value, including the user's own store, keeps CUA
  at 0 (EP). Requiring it only for authority arguments or document values lets stale
  values through (CaMeL + endorsement for all fact args: 3% CUA at ω = 0.5, because a
  store value passes as trusted). This is a difference in the rule's scope, not in the
  framework.

The ablations locate the rule:

* **Removing endorsement** (`EP w/o endorsement`) gives the same utility as
  `Reference-only`: 72.2%, which is −20.4 pp [−40.0, −3.2] at k = 4.
* **Requiring a unique confirmation** (`EP (unique confirmation)`) costs utility: −3.1 pp
  at k = 4, from safe abstentions on `B_flood` and `B_same_name_mule`.

## 5. What the audit changed (EP v0 → EP)

The pre-audit EP trusted an **uncontested** store value without verification, and bound
a **contested** store value once all challengers were refuted. The adversarial audit
(`09_audit_log.md`) showed that "uncontested" worked as an oracle for "fresh" in the
original suite. With the new variants, EP v0 is unsafe in 66 cases (14.4% CUA; 66
stale-value and 6 false-value commits):

| variant | EP v0 unsafe cases |
|---|---|
| `C_silent` | 24 of 27 |
| `C_suppressed` | 24 of 27 |
| `C_silent_attacked` | 12 of 27 |
| `B_same_name_mule` | 6 of 6 (challengers verified first) |

EP now requires evidence for store values too (strict R2), verifies the store first, and
uses a lookup when one is available. The cost is visible: safe failures on clean + C
rise from 0% to 14.6% at k = 4, and verification rises from 0.90 to 1.53 calls per case.
EP v0's higher utility at k = 2 (83.3% vs 82.1%) was bought with unsafe commits.

## 7. Assumption violations (§14; outside the guarantee)

| violation | EP | best other |
|---|---|---|
| **Stale reference** (225 C cases) | 97% CUA (stale commits); worse than No defense (47%) | Origin guard: 44% CUA, 52% utility |
| **Poisoned reference** (126 B cases) | 100% CUA | Origin guard: 21% CUA, 79% utility |
| **Reference outage** (486 cases) | 0% utility, 0% CUA | Origin guard: 67% utility, 31% CUA |
| **Same-principal compromise** (18 cases) | 100% CUA | Every design: 0% utility; CaMeL strong 83% CUA |

EP is exactly as good as its references. It fails worse than an undefended agent when a
reference is stale (97% vs 47% CUA; every verify-first design is at 87–97%). It is no
better than an undefended agent when a reference is poisoned (100% CUA for both); CaMeL
strong, Fides and Reference-only commit less often there (50–83%), because in some
slots they never bind a document value and abstain when the poisoned reference refutes
the user's record.

## 8. Cost

EP's LLM trace equals CaMeL's by construction: one planner call plus one reader call per
document, 2.65 calls per case. Its verification calls are the highest among the
existing-defense rows (1.53 per case at k = 4, against CaMeL strong's 1.40 and Fides
strong's 1.22). Fides is charged 5.1 LLM calls per case and AgentSentry 12.9. The LLM
counts are architecture labels (`05_baselines.md`), so the NO_GO rule also reports cost
with every planner charged once.
